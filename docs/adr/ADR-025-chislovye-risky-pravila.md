# ADR-025: числовые (не категориальные) RISKY-правила по heatResistance и strength

**Статус:** Согласовано.

## Context

Все предыдущие risky-правила Compatibility Engine (`CATEGORY_RELATIONS`) построены на паре вкусовых категорий (FRUIT+SOUR и т.д.). Отдельный аудит показал, что этот источник структурно исчерпан для нахождения новых RISKY-кандидатов: 37 verified-миксов по определению уже отобранные удачные рецепты (ни одного `negative` за всю историю), а внешние источники почти не содержат конкретных category-level claim'ов вида «X плохо сочетается с Y» (3 из 3 гипотез для FRUIT/TROPICAL не подтвердились).

Отдельная разведка предложила искать риск не в категориях, а в уже собранных числовых профилях 7 полей продукта (ADR-014: `sweetness`, `sourness`, `freshness`, `intensity`, `strength`, `heatResistance`, `juiciness`) — сами числа физически измеримы (жар, крепость), а не чужое мнение. Полный попарный прогон (C(86,2)=3655 пар зарегистрированных `RESOLVED`-продуктов) выявил два многообещающих поля:

- **heatResistance** (разница между компонентами) — 1176 пар с обоими значениями заполненными (32% охват), физически обоснован (один компонент прогорает/не раскрывается быстрее другого).
- **strength** (разница между компонентами) — 3486 пар (95% охват, лучший показатель среди всех 7 полей), сильный компонент забивает лёгкий.

Остальные 5 полей (`intensity` 3% пар, `sweetness`/`sourness`/`freshness`/`juiciness`) — либо недостаточное покрытие для честного порога, либо не нашли столь же ясного физического механизма — вне скоупа этой ADR.

Последующий анализ порогов (полная гистограмма Δ по всем 1176/3486 парам, не только топ-20) нашёл чёткий структурный разрыв на границе Δ=3→4 у **обоих** полей независимо:
- heatResistance: count(Δ=3)=287 → count(Δ=4)=90, отношение **3.19×** (самый резкий скачок в ряду).
- strength: count(Δ=3)=667 → count(Δ=4)=166, отношение **4.02×** (самый резкий скачок в ряду).

Оба порога согласуются с mean+1σ (3.61 и 3.11 соответственно), лежащим чуть ниже Δ=4. Внешние источники (Smoke Market, Felix Shop, Кальян Хат — те же, что цитировались для механизма) были отдельно проверены на наличие количественной шкалы жаростойкости — **не нашлось**, только качественные категории («высокая/умеренная жаростойкость» по брендам, без баллов/единиц). Поэтому порог обоснован статистически (структурный разрыв в распределении), а не внешней цитатой с числом.

## Decision

1. **Порог Δ≥4 для обоих полей**, обоснование — структурный разрыв распределения (не внешний количественный источник, которого нет).
2. Новый, отдельный evidence-tier `statisticalThreshold()` в `src/lib/flavor-knowledge/numeric-risk-rules.ts` (новый файл, не `category-relations.ts` — вход другой: числовое поле+порог, а не пара категорий). Эвиденс-префикс `evidence.statistical-threshold.*` — **намеренно не** `HIGH`/`MEDIUM`/`LOW`/`SINGLE_PRODUCT_MARKETING` из `researched()`/`verifiedHistory()`: это другая по природе метрика (распределение+структурный разрыв, а не оценка достоверности заявленной связи), совпадение по силе с этими тирами не подразумевается.
3. `baseScore = -0.4` для обоих правил — то же порядок величины, что и мода существующих RISKY-баллов в `category-relations.ts` (`-0.4` встречается чаще всего среди RISKY-записей, `-0.5` — единичные исключения). Не выдумано отдельно.
4. Правило срабатывает по **одной, самой экстремальной** паре компонентов на правило (тот же паттерн, что и категориальный цикл — «один матч на правило»), а не суммируется по всем парам, пересекшим порог, — избегает переусиления импакта на мультикомпонентных миксах.
5. Числовые правила читают **эффективный** (`effectiveProfile.profile`, после ADR-023 null-preserving разрешения кандидатов), а не сырой Prisma-профиль компонента — это тот же профиль, который использует весь остальной движок; ADR-023 уже гарантирует, что немзмеренное поле остаётся `null`, а не заменяется угадыванием.
6. Результат числового правила **вливается в существующий блок `noteCompatibility`** (score/warnings/appliedRules), а не в новый пятый scored-блок `MixCompatibilityResult`. Причина — новый блок потребовал бы пересчитывать `COMPATIBILITY_WEIGHTS` (сейчас 4 блока в сумме дают 1.0) и трогать каждого потребителя ровно 4 именованных блоков (canonical-mix-scoring, mix-recommendation, mix-result-presentation) — несоразмерно задаче «добавить 2 правила». Сама логика оценки (`evaluateNumericRiskRules`) при этом — отдельная, явно названная функция, не встроена в цикл `analyzeNoteCompatibility` над нотами (разные входные данные: числовой профиль компонента, а не список назначенных категорий заметок).
7. Presentation: новое поле `matchedNumericRisks` на `MixCompatibilityResult`/`MixResultPresentation` — pass-through (не пересканирование, в отличие от `matchedCategoryPairs` из ADR-024), так как конкретные значения уже вычислены на этапе scoring и не выводятся из статичной таблицы правил. Рендерится тем же CSS-only tooltip-паттерном (ADR-022/024), новый набор классов `.numeric-risk-*` (скопированы 1:1 из `.category-match-*`), в секции «Риски».
8. Числовое RISKY-срабатывание автоматически появляется и в обычном списке «Риски» — `groupCompatibilityRisks` (`canonical-mix-scoring/risk-groups.ts`) уже обобщённо фильтрует `compatibility.warnings` по `impact<0`, без category-специфичной логики, поэтому новое правило подхватывается без изменений в этом модуле.

## Alternatives considered

- **Новый пятый top-level scored-блок (`numericRisk`) в `MixCompatibilityResult`.** Отклонено: требует пересчёта `COMPATIBILITY_WEIGHTS` и правки всех потребителей 4 именованных блоков — несоразмерно задаче.
- **Переиспользовать `HIGH`/`MEDIUM`/`LOW` как есть для этого evidence-tier.** Отклонено явно постановкой — визуально создало бы впечатление того же по силе тира, что у `researched()`/`verifiedHistory()`, хотя природа evidence другая (статистика+качественный механизм, не оценка достоверности претензии).
- **Сырой `component.profile.heatResistance`/`.strength` вместо `effectiveProfile.profile`.** Отклонено: `effectiveProfile` — единственный профиль, который остальной движок считает авторитетным для компонента (после разрешения кандидатов/fallback), и уже даёт null-safety по ADR-023 бесплатно.
- **Масштабировать impact правила по доле компонентов в миксе (как у категориальных note-правил).** Отклонено для этой итерации — не специфицировано ADR, добавило бы неформализованную формулу; полный `baseScore` применяется без масштабирования.

## Consequences

- `category-relations.ts`/`CATEGORY_RELATIONS`/категориальные правила не изменены.
- Компоненты без измеренного heatResistance/strength у обоих участников пары просто не участвуют в этом конкретном правиле (пропуск, не 0/среднее).
- Единственный новый top-level тип поля — `matchedNumericRisks` на `MixCompatibilityResult`; существующие фикстуры-моки этого типа в тестах (`canonical-mix-scoring/calculate-canonical-mix-score.test.ts`, `canonical-mix-scoring/risk-groups.test.ts`) обновлены механически (`matchedNumericRisks: []`), поведение тестов не менялось.
- `numericProfiles` — опциональное поле `MixCompatibilityInput`; все вызовы, предшествующие ADR-025, продолжают работать без изменений (числовое правило просто никогда не срабатывает без него).
