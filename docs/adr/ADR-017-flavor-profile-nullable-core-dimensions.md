# ADR-017: nullable core-измерения `FlavorProfile` — расширение политики ADR-015 на все 18 полей

## Context

ADR-015 сделала nullable 11 «несобираемых» второстепенных полей `FlavorProfile`/Prisma `Flavor`, оставив 7 core-полей ADR-014 (`strength`, `heatResistance`, `intensity`, `sweetness`, `acidity`, `juiciness`, `freshness`) обязательными — обоснование было в том, что для этих 7 полей «есть реальный класс источников для большинства продуктов».

При проектировании импортёра Product Flavor Profile Registry → Prisma `Flavor` (реализующего политику ADR-016) обнаружилось, что «есть реальный класс источников для большинства продуктов» — это утверждение про существование источника в принципе, а не про фактическую заполненность каждого конкретного продукта. На практике распределение по всем 86 `RESOLVED`-продуктам (число заполненных из 7 core-измерений → количество продуктов) таково:

| Заполнено core-измерений | Продуктов |
|---|---|
| 0 | 1 |
| 1 | 6 |
| 2 | 20 |
| 3 | 27 |
| 4 | 20 |
| 5 | 8 |
| 6 | 4 |
| 7 | 0 |

Ни один продукт не имеет всех 7 core-полей заполненными; один продукт (`dozaj-mint`) не имеет заполненным ни одного (после исключения контаминированных cross-brand источников — см. `docs/engine-changelog/v0.3.5-product-flavor-profile-registry-batch-4.md`). При этом ADR-016 явно требует импортировать все 86 продуктов независимо от заполненности (0–6, а не только «полные» профили) — иначе жёсткий порог отсекал бы больше половины registry по причине отсутствия источника, а не низкого качества данных.

Оставить core-поля обязательными в Prisma и одновременно выполнить это требование ADR-016 невозможно без нарушения ключевого принципа проекта (ADR-003, подтверждённого в ADR-014/015): **никогда не изобретать значение при молчании источника**. Единственный способ честно импортировать продукт с 0–6 из 7 заполненных core-полей — записать `null` в оставшиеся, то есть сделать эти 7 полей nullable точно так же, как это уже сделано для 11 второстепенных.

## Decision

1. Оставшиеся 7 полей ADR-014 (`strength`, `heatResistance`, `intensity`, `sweetness`, `acidity`, `juiciness`, `freshness`) становятся `Float?` в Prisma `Flavor` — той же отдельной миграцией, независимо не совмещаемой ни с чем другим. Теперь **все 18** числовых сенсорных полей `Flavor` nullable.
2. Политика «`null` = не измерено, никогда не 0» (ADR-015, п. 3) распространяется на эти 7 полей без изменений — та же явная обязанность для каждого потребителя: агрегации исключают `null` из числителя и знаменателя, пороговые правила не срабатывают на `null`, презентационный слой показывает явное «не измерено», а не вычисленное число.
3. Различие «core / secondary» из ADR-014 остаётся содержательным только на уровне **Product Flavor Profile Registry** (какие 7 из 18 вообще входят в целевую модель registry и почему остальные 11 в неё не входят — см. ADR-014) и как справочные константы (`FLAVOR_PROFILE_CORE_FIELDS`/`FLAVOR_PROFILE_SECONDARY_FIELDS` в `src/lib/flavors/types.ts`, полезные, например, импортёру для выбора, какие 7 полей брать из registry). На уровне же самого типа `FlavorProfile` это различие больше не выражается в типах: тип упрощается обратно до единого `Record<FlavorProfileField, number | null>` для всех 18 полей — раздельная intersection-форма (`Record<Core,number> & Record<Secondary,number|null>`), введённая ADR-015, перестаёт быть нужна, потому что обе части теперь имеют одинаковую форму значения.
4. `validate-flavor.ts` и все прочие валидационные границы (`mix-profile/validate-input.ts`, `mix-recommendation/calculate-recommendations.ts`) применяют одно и то же правило ко всем 18 полям: валидно, если `null`, либо конечное число 0–10.
5. Аудит потребителей выполняется тем же методом, что и в ADR-015: `tsc --noEmit` как источник истины (а не список файлов, написанный заранее), с построчной проверкой каждой найденной ошибки и явным null-guard'ом там, где он нужен по существу, а не формально.
6. Существующие demo/seed-строки `Flavor` (16 записей `prisma/seed.ts`) не меняются — как и в ADR-015, nullable ≠ обязан быть null; все demo-значения остаются заполненными.

## Consequences

- `canonical-mix-scoring/build-effective-tobacco-profile.ts` уже содержит generic-цикл по `FLAVOR_PROFILE_FIELDS` (все 18) с каскадным резолвером (`Number.isFinite` → `CANONICAL_TECHNICAL_PROFILE` → `NEUTRAL_FALLBACK=5`) — этот код не требует изменений: он уже одинаково обрабатывает `null` для любого из 18 полей, независимо от того, что раньше 7 из них физически не могли быть `null`. Это значит, что в реальном production-пайплайне `calculateMixAnalysis` core-поля так же, как и раньше secondary, всегда резолвятся в реальное число до того, как дойдут до scoring/compatibility/recommendation/presentation слоёв.
- Ровно то же следствие, что и в ADR-015: большинство guard'ов в `analyze-profile-balance.ts`, `summary-tags.ts`, `mix-recommendation/*`, `mix-result-presentation/index.ts` для НОВО-nullable core-полей (`sweetness`, `acidity`, `freshness`, `intensity`, `strength`, `heatResistance`, `juiciness`) — это укрепление типовой корректности и явности, а не исправление живого рантайм-бага в основном пайплайне; настоящий, ничем не резолвимый риск остаётся сосредоточен в устаревшем `mix-analyzer.ts` (получает «сырые» Prisma-данные напрямую, без каскада) и на границах входной валидации.
- Импортёр Product Flavor Profile Registry (ADR-016) может теперь честно записывать `null` в любое из 18 полей, включая core, без нарушения схемы и без выдумывания чисел — именно это и было причиной этой ADR.
- `FlavorProfile` как тип становится проще (единый `Record`), но код, который раньше полагался на компилятор для гарантии «core всегда число» (например, арифметика без явных проверок), теперь обязан either явно проверять `!== null`, либо документированно полагаться на то, что данные уже прошли через `buildEffectiveTobaccoProfile`.

## Alternatives considered

- **Импортировать только продукты с полным набором из 7 core-полей.** Отклонено: таких продуктов 0 из 86 — это эквивалентно «не импортировать вообще ничего», что прямо противоречит требованию ADR-016 охватить все 86 продуктов.
- **Подставлять нейтральное значение-заглушку (например, 5) для отсутствующих core-полей при импорте.** Отклонено: то же рассуждение, что уже отклонило аналогичный вариант в ADR-015 и саму мотивацию ADR-003/014 — заглушка неотличима ниже по стеку от реально измеренного значения, то есть отсутствие данных навсегда превращается в предъявляемый факт.
- **Оставить core-поля обязательными в Prisma, но сделать `FlavorProfile` (доменный TS-тип) nullable только «для импортёра», через отдельный входной тип.** Отклонено: реальное ограничение — это NOT NULL в самой колонке Prisma, отдельный TS-тип не решает вопрос записи `null` в обязательную колонку; протащить два параллельных типа `FlavorProfile` (для чтения и для импорта) создало бы путаницу и разошлось бы с уже существующим единым типом, используемым всем стеком scoring/compatibility/recommendation.
- **Сохранить различие core/secondary в самой форме типа (intersection), просто расширив «nullable-часть» на все 18 полей.** Отклонено как избыточное: если ВСЕ поля имеют одинаковую форму значения (`number | null`), раздельные `Record`-части в intersection ничего не выражают, кроме исторического деления, которое и так остаётся зафиксированным в отдельных константах `FLAVOR_PROFILE_CORE_FIELDS`/`FLAVOR_PROFILE_SECONDARY_FIELDS`.
