# ADR-018: перенос `dominantNoteIds` Product Flavor Profile Registry в Prisma `FlavorNoteAssignment`

## Context

Диагностика на живой базе после импорта ADR-016 (86 продуктов, `--apply` выполнен) показала подозрительно узкий диапазон предсказанного скора (`predictedQualityScore`) на новых продуктах — 7.5–7.8 на выборке из 12 пар, что даже уже, чем плоский диапазон 7.5–7.9 из диагностики v0.3.3, несмотря на наличие реальных evidence-based данных по 7 core-полям.

Причина найдена и проверена напрямую на реальном пайплайне (`calculateMixAnalysis`), без изменения кода:

**Ни один из 86 импортированных продуктов не имеет ни одной записи в `FlavorNoteAssignment`.** Спецификация импортёра ADR-016 (`scripts/import-product-flavor-profiles.ts`) осознанно ограничивалась 7 core-полями `Flavor` — перенос `dominantNoteIds` в таблицу нот не входил в её объём и не был реализован. В результате `buildEffectiveTobaccoProfile` для каждого нового продукта не находит ни одного кандидата с непустым `notes[]` и подставляет синтетический fallback: `category: "OTHER"`, `reliabilityScore: 15`. Это воспроизводится **на всех 85 новых продуктах без исключения** — категория `OTHER` и `usedFallback: true` для note-кандидата присутствуют в каждой из 12 продиагностированных пар.

Следствие для scoring: `noteCompatibility` (один из четырёх компонентов `compatibilityScore`, вес `0.4`) стартует с базового значения `BASE_SCORES.noteCompatibility = 7` и остаётся на этом уровне, потому что ни одно правило `NOTE_COMPATIBILITY_RULES` не матчится на категорию `OTHER` — она не упомянута ни в одном селекторе. Это и даёт наблюдаемую пиковую однородность: качественная (note/category) часть compatibility-скоринга сейчас **полностью отключена** для всех продуктов реестра, варьируется только числовая часть (profileBalance/intensityBalance) на основе частично заполненных 7 core-полей.

При проектировании переноса обнаружены два дополнительных факта, меняющих объём задачи по сравнению с «просто скопировать значения»:

**1. Расхождение словарей категорий.** `dominantNoteIds` в `PRODUCT_FLAVOR_PROFILE_REGISTRY` типизирован как `readonly FlavorNoteCategory[]` из `flavor-knowledge` (25 значений: `FRUIT, BERRY, CITRUS, TROPICAL, FLORAL, HERBAL, MINT, COOLING, SPICE, DESSERT, CREAMY, VANILLA, BEVERAGE, TEA, COFFEE, NUT, BAKERY, CANDY, CHOCOLATE, ALCOHOL, WOODY, SMOKY, TOBACCO, SOUR, FRESH`). Колонка `FlavorNote.category` в Prisma использует **другой**, более узкий enum `FlavorNoteCategory` (16 значений: `FRUIT, BERRY, CITRUS, DESSERT, DRINK, SPICE, FLORAL, HERBAL, COOLING, NUT, COFFEE, CHOCOLATE, DAIRY, TROPICAL, SMOKY, OTHER`). Существующая функция `toKnowledgeCategory`/`LEGACY_CATEGORY_MAP` покрывает перевод только в одну сторону (legacy → knowledge) и только для 15 значений.

Фактическое использование `dominantNoteIds` по всем 86 продуктам (184 объявления, продукт может иметь несколько доминирующих категорий):

| Категория | Употреблений | Есть аналог в Prisma-enum? |
|---|---|---|
| FRUIT | 38 | да |
| CREAMY | 16 | да (→ `DAIRY`) |
| SOUR | 14 | **нет** |
| TROPICAL | 13 | да |
| CITRUS | 13 | да |
| BERRY | 13 | да |
| DESSERT | 12 | да |
| CANDY | 11 | **нет** |
| COOLING | 6 | да |
| SPICE | 5 | да |
| NUT | 5 | да |
| MINT | 5 | **нет** |
| WOODY | 4 | **нет** |
| TEA | 4 | **нет** |
| FRESH | 4 | **нет** |
| BAKERY | 4 | **нет** |
| ALCOHOL | 4 | **нет** |
| HERBAL | 3 | да |
| VANILLA | 2 | **нет** |

**9 из 24 использующихся категорий (52 из 184 объявлений, ≈28%) не имеют значения в текущем Prisma-enum вообще** — `SOUR`, `CANDY`, `MINT`, `TEA`, `FRESH`, `BAKERY`, `ALCOHOL`, `WOODY`, `VANILLA`. Это не было видно на уровне ADR-016 (которая не касалась нот) и обнаружено только сейчас, при проектировании самого переноса.

**2. `CATEGORY_RELATIONS` почти не используется движком.** В `src/lib/flavor-knowledge/category-relations.ts` определено 23 связи между категориями (включая гипотетическую `FLORAL+CREAMY`, которой там **нет вообще**, ни в каком направлении — только `FLORAL–SMOKY: RISKY` и `FLORAL–COOLING: RISKY`). Но реальный список правил, который читает `analyzeNoteCompatibility` — `NOTE_COMPATIBILITY_RULES` в `compatibility-rules.ts` — подключает через `createKnowledgeCategoryRule(...)` только **2 из 23** связей (`BERRY+FLORAL`, `COFFEE+CITRUS`). Остальные 21 существуют в `CATEGORY_RELATIONS` только для прямых вызовов `getCategoryRelation()`, но не участвуют в скоринге миксов. Это значит, что «добавить связь в `CATEGORY_RELATIONS`» и «связь реально влияет на `compatibilityScore`» — два разных, независимых шага.

**3. Существует пригодный для переиспользования прецедент.** В demo-данных уже есть несколько нот, названных ровно как категория в нижнем регистре и явно играющих роль «общей» ноты категории: `fruit`/`FRUIT`, `berry`/`BERRY`, `citrus`/`CITRUS`, `dessert`/`DESSERT`, `spice`/`SPICE`, `herbal`/`HERBAL`, `tropical`/`TROPICAL`, `coffee`/`COFFEE` (8 категорий). Остальные категории представлены только специфичными нотами (`cream`/`milk` под `DAIRY`, `cocoa`/`dark chocolate` под `CHOCOLATE`, `hazelnut` под `NUT`, `mint` под `COOLING`, `roasted` под `SMOKY`, `cola` под `DRINK`, `vanilla` под `DESSERT`) или не представлены вовсе (`FLORAL`). Все 17 существующих `DOMINANT`-назначений в базе используют `intensity: 10` без исключений — это уже сложившаяся, а не изобретаемая конвенция.

## Decision

### 1. Механизм — отдельный скрипт, не расширение импортёра ADR-016

Перенос категорий реализуется как **отдельный** скрипт `scripts/import-product-flavor-note-assignments.ts` с собственным чистым планировщиком `src/lib/product-flavor-profile-note-import/` (по образцу `src/lib/product-flavor-profile-import/`: `types.ts`, `build-note-import-plan.ts`, `index.ts`, тесты — вся логика планирования не обращается к Prisma напрямую).

Причины не расширять `scripts/import-product-flavor-profiles.ts`:
- Разные таблицы и разная модель изменений: основной импортёр пишет 18 скалярных полей `Flavor`; этот — создаёт связи `Flavor ↔ FlavorNote` через `FlavorNoteAssignment`, потенциально создавая новые строки `FlavorNote`. Смешение в одном скрипте усложнило бы и без того нетривиальную CREATE/UPDATE/SKIPPED_TEST-логику основного импортёра без выигрыша.
- Основной импортёр уже реализован, протестирован (18 тестов) и применён к базе (`--apply` выполнен, коммит зафиксирован) — трогать его код ради несвязанной задачи means повторное код-ревью уже сданной части.
- Идентификация целевых строк для нового скрипта отличается: он всегда работает по уже существующим (`canonicalProductId IS NOT NULL`) строкам `Flavor` — CREATE/UPDATE-ветвление ему не нужно, только «есть нужное назначение — пропустить, нет — создать».

Скрипт наследует уже принятые в проекте конвенции: `--dry-run` (по умолчанию) / `--apply`, никогда не удаляет существующие `FlavorNoteAssignment` (в том числе созданные вручную для demo-строк), идемпотентен (повторный запуск не создаёт дублей — проверка по паре `flavorId + flavorNoteId`), выводит отчёт (сколько назначений создастся, по каким категориям, какие продукты без единого распознанного `dominantNoteId` — для тех `FLORAL/CREAMY`-подобных пар статус останется прежним и это должно быть видно в отчёте явно, а не молчать).

Источник и охват те же 86 `RESOLVED`-решений, что и в ADR-016/основном импортёре — сопоставление по `canonicalProductId`, который уже проставлен на всех 85 CREATE + 1 UPDATE строках. Demo-строка `Daily Hookah / Сливки` (не импортированная, `canonicalProductId IS NULL`, near-duplicate из review-списка ADR-016 п.4) вне охвата этого скрипта — у неё уже есть свои ноты (`cream`, `milk` — `DAIRY`), трогать её не требуется и не следует.

### 2. Расхождение словарей — расширить Prisma-enum `FlavorNoteCategory`, не терять и не искажать данные

Для 9 категорий без прямого аналога (`SOUR`, `CANDY`, `MINT`, `TEA`, `FRESH`, `BAKERY`, `ALCOHOL`, `WOODY`, `VANILLA`) выбрано **добавить недостающие значения в Prisma enum `FlavorNoteCategory`** через аддитивную миграцию (`ALTER TYPE "FlavorNoteCategory" ADD VALUE ...` — не удаляет и не переименовывает существующие значения, обратно совместимо, существующие 27 строк `FlavorNote` не затрагиваются). Имена новых значений enum совпадают буквально с именами категорий `flavor-knowledge` (`SOUR`, `CANDY`, `MINT`, `TEA`, `FRESH`, `BAKERY`, `ALCOHOL`, `WOODY`, `VANILLA`) — по той же схеме 1:1, что уже используется для 13 из 15 существующих сопоставлений в `LEGACY_CATEGORY_MAP`.

`LEGACY_CATEGORY_MAP` (`src/lib/flavor-knowledge/note-taxonomy.ts`) расширяется этими 9 парами, так что `toKnowledgeCategory` начинает распознавать их наравне с существующими 15 — это делает всю уже написанную knowledge-layer-инфраструктуру (`getCategoryRelation`, `createKnowledgeCategoryRule`) применимой и к новым категориям без дополнительных изменений в её собственной логике.

Отклонённая альтернатива — маппинг «в ближайшую существующую категорию» (например, `SOUR → CITRUS`, `CANDY → DESSERT`, `MINT → COOLING`) — рассмотрена и отклонена: это тот же принцип, что уже отверг ADR-015/017 для числовых `null` — искажать evidence, подгоняя его под ближайшую существующую метку, хуже, чем явно расширить модель. `SOUR` не всегда цитрусовый (например, кислые леденцы), `CANDY` не всегда десертный по фактуре — навязанное отождествление создало бы неверные срабатывания правил там, где реального совпадения категорий нет.

### 3. Generic-ноты на категорию — переиспользовать существующие, создать недостающие

`dominantNoteIds` в реестре — это категории, а не конкретные ноты (`"FLORAL"`, а не `"lavender"`), поэтому для каждой из 24 использующихся категорий нужна ровно одна «представительская» строка `FlavorNote`, на которую будут указывать все `FlavorNoteAssignment` этой категории:

| Категория (knowledge) | Prisma-категория | Действие |
|---|---|---|
| FRUIT, BERRY, CITRUS, DESSERT, SPICE, HERBAL, TROPICAL, COFFEE | те же имена (существуют) | переиспользовать существующие generic-ноты (`fruit`, `berry`, `citrus`, `dessert`, `spice`, `herbal`, `tropical`, `coffee`) |
| CREAMY | `DAIRY` (существует) | создать новую generic-ноту (`cream`/`milk` — специфичные, не подходят как представитель категории целиком) |
| CHOCOLATE | `CHOCOLATE` (существует) | создать новую generic-ноту (`cocoa`/`dark chocolate` — специфичные) |
| NUT | `NUT` (существует) | создать новую generic-ноту (`hazelnut` — специфичная) |
| FLORAL | `FLORAL` (существует, но без единой ноты) | создать новую generic-ноту |
| COOLING | `COOLING` (существует) | создать новую generic-ноту (`mint` — специфичная нота, не тождественна всей категории `COOLING`) |
| SMOKY | `SMOKY` (существует) | создать новую generic-ноту (`roasted` — специфичная) |
| BEVERAGE | `DRINK` (существует, перевод по карте) | создать новую generic-ноту (`cola` — специфичная) |
| SOUR, CANDY, TEA, FRESH, BAKERY, ALCOHOL, WOODY | новые значения enum (п.2) | создать по одной новой generic-ноте на каждую |
| MINT | новое значение enum `MINT` | создать новую generic-ноту **с отдельным slug**, не путать с существующей нотой `mint`/`COOLING` — это разные записи: одна представляет категорию `COOLING` (уже есть), другая — новую категорию `MINT` |
| VANILLA | новое значение enum `VANILLA` | создать новую generic-ноту **с отдельным slug**, не путать с существующей нотой `vanilla`/`DESSERT` |

Все новые `FlavorNoteAssignment` создаются с `noteType: "DOMINANT"`, `intensity: 10` — это единственное значение, которое сегодня использует любая существующая `DOMINANT`-запись в базе (17 из 17), явно вводить отдельную шкалу интенсивности не для чего: у реестра нет per-note интенсивности, только сам факт «это доминирующая категория».

### 4. `CATEGORY_RELATIONS` (например, `FLORAL+CREAMY`) — вне объёма этой ADR, отдельная будущая задача

Эта ADR **не добавляет** новых записей в `CATEGORY_RELATIONS` и не трогает `NOTE_COMPATIBILITY_RULES`. Причины:
- Добавление связи — это content-решение («эта пара категорий обычно хорошо сочетается / рискованна / конфликтует»), требующее собственного обоснования (evidence/экспертное правило), а не механическое следствие того, что теперь у продуктов есть категории. Молчаливо добавить `FLORAL+CREAMY: RISKY` вместе с чисто технической задачей переноса означало бы протащить непроверенное вкусовое суждение без отдельного review — тот же принцип, что уже применялся к почти-дублям в ADR-016 п.4 («решение о содержании — не автоматически, а отдельным явным шагом»).
- Как показано в Context (п.2), даже наличие записи в `CATEGORY_RELATIONS` не гарантирует её применения — нужен ещё явный `createKnowledgeCategoryRule(...)` в `compatibility-rules.ts`. Это второй, тоже content-уровня шаг.
- После этой ADR `FLORAL` и `CREAMY`(`DAIRY`) категории у продуктов наконец будут видны движку корректно — пара из диагностики (`Sarma Горная лаванда` + `Daily Hookah Сливки`) при повторном прогоне покажет реальные категории `FLORAL`/`DAIRY` вместо `OTHER`, но по-прежнему не будет отмечена как рискованная, пока кто-то явно не решит вопрос «должна ли она быть отмечена» и не заведёт для этого отдельную ADR/задачу с конкретным списком новых связей.

## 5. Ожидаемый эффект на `usedFallback`/reliability и диапазон scoring

Важно не переобещать: у этой ADR два независимых канала влияния на `predictedQualityScore`, и они затрагивают разные вещи.

**Что НЕ изменится.** `usedFallback` в `EffectiveTobaccoProfile` — это `OR` по двум независимым условиям: `NEUTRAL_FALLBACK` сработал хотя бы для одного из 18 числовых полей **или** для note-кандидата. Все 85 новых продуктов по-прежнему имеют от 0 до 6 из 7 core-полей и **все 11** secondary-полей `null` (по политике ADR-016 п.2 — второстепенные поля всегда `null` при импорте). Значит числовая часть `usedFallback` продолжит быть `true` почти для каждого продукта независимо от этой ADR — она не решает проблему неполноты числовых измерений, только проблему категорий/нот.

**Что изменится.** Note-кандидат для продукта с хотя бы одним распознанным `dominantNoteId` перестанет быть `NEUTRAL_FALLBACK` (`reliabilityScore: 15`, `category: "OTHER"`) и станет `SOURCE_PROFILE` (`reliabilityScore: 60` — стандартная надёжность для `profileStatus: DRAFT`/`profileSource: MIXED`, см. `reliability()` в `from-prisma.ts`) с реальной категорией. Это включает качественную часть compatibility-скоринга (`noteCompatibility`, вес `0.4` внутри `compatibilityScore`, которая сама весит `0.25` в `predictedQualityScore`) для пар, где сработает хотя бы одно из уже существующих 2 подключённых правил (`BERRY+FLORAL`, `COFFEE+CITRUS`) или одно из ~15 hand-authored правил `NOTE_COMPATIBILITY_RULES` (`coffee-dairy`, `dairy-cooling`, `floral-smoky` и т.д. — они матчатся по категориям напрямую, без `CATEGORY_RELATIONS`).

**Количественная оценка диапазона.** Прямое плечо влияния через `noteCompatibility` на итоговый `predictedQualityScore` ограничено `0.4 × 0.25 = 0.10` (10%) от шкалы 0–10, то есть до ≈1 балла в одну сторону при полном срабатывании положительного/рискованного правила на паре, плюс небольшой второй эффект через `risks` (вес `0.1`) для тех пар, где сработавшее правило — `conflict`, а не `caution`. Реалистичное ожидание: диапазон 7.5–7.8, наблюдаемый сейчас на 12 парах, **должен расшириться** — пары, где оба компонента получат категории с реальным совпадающим правилом (например, `COFFEE` + `DAIRY` → правило `note.coffee-dairy`, `+0.7`), пойдут заметно выше текущего плоского уровня; пары с `caution`/`conflict`-правилами (`floral-smoky`, `herbal-dessert`, `dairy-cooling`) — заметно ниже. Пары, у которых нет ни одного матчащегося правила между их конкретными категориями (в том числе исходная `Sarma+Сливки`, пока `FLORAL+CREAMY` не заведена отдельно — см. п.4), останутся примерно на нынешнем базовом уровне `noteCompatibility ≈ 7` — то есть диапазон расширится, но не факт, что охватит все 86 продуктов одинаково: это ожидаемо и честно отражает то, что часть пар сочетаний реестра пока не покрыта ни одним content-правилом ни в одном направлении.

## Consequences

- Появляется вторая, независимая от основного импортёра точка входа в Prisma для тех же 86 продуктов — оба скрипта должны запускаться в связке (`import:product-flavor-profiles --apply`, затем `import:product-flavor-note-assignments --apply`) при любом будущем повторном импорте новой партии решений; это стоит явно задокументировать в runbook/README, а не полагаться на память.
- Prisma-миграция `ALTER TYPE ... ADD VALUE` — аддитивная и не ломает существующие данные, но `ADD VALUE` для enum в PostgreSQL нельзя выполнить в той же транзакции, где значение уже используется — при написании миграции это должно быть отдельным migration-файлом перед файлом, который создаёт `FlavorNote`-строки с новыми значениями (иначе миграция упадёт).
- Расширение `FlavorNoteCategory` затрагивает общий enum, потребитель которого — не только этот скрипт: `compatibility-rules.ts`, `note-taxonomy.ts`, любые будущие demo/seed-правки. Потребуется по аналогии с ADR-015/017 прогнать `tsc --noEmit` и полный набор тестов после расширения enum, а не полагаться на то, что 9 новых значений «просто добавляются» без побочных эффектов (например, exhaustiveness-проверки через `switch`, если такие есть где-то в кодовой базе).
- До отдельной будущей ADR по `CATEGORY_RELATIONS`/`NOTE_COMPATIBILITY_RULES` часть новых категорий (в первую очередь только что заведённые `SOUR`, `CANDY`, `MINT`, `TEA`, `FRESH`, `BAKERY`, `ALCOHOL`, `WOODY`, `VANILLA`) не будут участвовать ни в одном правиле совместимости вообще — у них корректная категория появится, но `noteCompatibility` для пар с этими категориями не изменится, пока для них не появятся конкретные правила.
- Проверено: все 86 продуктов реестра имеют непустой `dominantNoteIds` (ни одного продукта с `[]`), так что после этой ADR ни один из 86 не должен остаться с синтетической категорией `OTHER` по причине отсутствия данных в реестре — если такой случай всё же появится в будущих партиях, отчёт скрипта обязан показывать его явно, а не маскировать.

## Alternatives considered

- **Расширить существующий импортёр `import-product-flavor-profiles.ts` вместо отдельного скрипта.** Отклонено: разные Prisma-модели, разная логика (нет CREATE/UPDATE-ветвления для нот), уже сданный и протестированный код основного импортёра пришлось бы трогать ради несвязанной функциональности.
- **Смэппить 9 категорий без Prisma-аналога в ближайшую существующую (`SOUR→CITRUS` и т.д.).** Отклонено: искажает evidence тем же способом, что ADR-015/017 запретили для числовых `null→0`; ложные срабатывания/несрабатывания правил совместимости хуже, чем явное расширение enum.
- **Не заводить generic-ноты, находить/создавать конкретную ноту под каждый реальный продукт (например, отдельная нота `lavender` для Sarma).** Отклонено на этом шаге: `dominantNoteIds` реестра — это категории, а не конкретные вкусовые ноты (у registry нет данных на уровне «это именно лаванда», только «это цветочная категория»); придумывать конкретное название ноты сверх того, что подтверждено evidence, было бы тем же нарушением принципа «не изобретать факты», от которого проект последовательно уклоняется с ADR-003.
- **Включить в эту ADR добавление `FLORAL+CREAMY` и других недостающих связей в `CATEGORY_RELATIONS`.** Отклонено: content-решение, требующее собственного обоснования, вне объёма чисто технического переноса категорий; риск протащить непроверенное вкусовое суждение без отдельного review.
- **Ничего не делать и полагаться только на будущее наполнение числовых полей.** Отклонено: диагностика показала, что даже при полном заполнении 7 core-полей `noteCompatibility` (40% веса `compatibilityScore`) останется замороженным на базовом значении для всех продуктов без единого исключения — числовая часть одна не может исправить симптом, вызванный отсутствующим качественным сигналом.
