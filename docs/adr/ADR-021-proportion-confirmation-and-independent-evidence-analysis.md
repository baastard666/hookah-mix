# ADR-021: `proportionConfirmed`/`independentEvidenceCount` — анализ источников данных (без реализации)

## Context

Диагностика всех 6 компонентов `predictedQualityScore` на 12 реальных парах (после ADR-020) показала: `confirmations` — **ровно `5.0` для всех 12 пар без единого исключения**, и отдельная проверка (одна и та же пара при 50/50, 80/20, 30/70, 95/5) подтвердила: значение не сдвигается ни на 0.1 вообще ни при каком процентном соотношении. Причина найдена в коде, не в данных: `fromPrismaFlavor` (`src/lib/mix-profile/from-prisma.ts`) — функция, которую использует **весь** живой путь построения микса из реальной строки `Flavor` (`src/app/api/mixes/route.ts`), — никогда не устанавливает `proportionConfirmed`/`independentEvidenceCount`. Оба поля опциональны и по умолчанию превращаются в `false`/`0` (`prepare-canonical-mix.ts:31`), поэтому `confirmationScore()` (`calculate-canonical-mix-score.ts`) всегда считает `5 + 0 + 0 = 5`.

**Это не специфично для новых 86 продуктов и не связано с ADR-018/019/020** — касается вообще любого микса, построенного через реальный API, включая исходные demo-товары.

### У этих двух полей — два потребителя, не один

1. `calculateCanonicalMixScore` → `scoreBreakdown.confirmations` — **10% веса** `predictedQualityScore` (`MIX_SCORE_WEIGHTS.confirmations = 0.1`).
2. `calculateMixConfidence()` (`calculate-mix-confidence.ts`) → `proportionCoverage` (**15% веса** этой отдельной формулы) и `externalEvidenceCoverage` (**10% веса**) → `predictionConfidence.finalConfidenceLabel` («Предварительная»/«Средняя»/«Высокая»/«Подтверждённая») — отдельный, показываемый пользователю лейбл уверенности, не влияющий на сам `predictedQualityScore`, но формирующий отдельное впечатление о микс.

Второй потребитель страдает сильнее и это стоит явно посчитать. Для любого микса, целиком состоящего из товаров с `profileStatus=DRAFT`/`profileSource=MIXED` (то есть **всех 86 новых импортированных продуктов** — `reliability()` даёт им фиксированные 60), максимально достижимая уверенность сегодня:

```
identityCoverage(100%)×0.4 + profileCoverage(60)×0.35 + proportionCoverage(70,зафиксировано)×0.15 + externalEvidenceCoverage(0,зафиксировано)×0.1
= 40 + 21 + 10.5 + 0 = 71.5
```

Порог «Высокая» — `≥75`. **Ни один микс, целиком состоящий из новых 86 продуктов, не может достичь лейбла «Высокая» ни при каких обстоятельствах** — не из-за качества самого микса, а исключительно из-за двух зафиксированных на месте полей.

### Проверено: только `proportionConfirmed` вообще где-то реально вычисляется — и только не в живом пути

Единственное место в кодовой базе, где `proportionConfirmed` получает содержательное (не заглушечное) значение — `workbook-audit.ts:65`, и означает оно узкую вещь: *«сумма процентов компонентов исторического verified-микса из workbook равна 100%»* — проверка целостности РЕЦЕПТА, а не независимое подтверждение качества сочетания.

`independentEvidenceCount` **не устанавливается в ненулевое значение вообще нигде в проекте** — включая `workbook-audit.ts`, единственный путь, который хоть немного заботится о первом поле. Более того, есть ВТОРОЕ, параллельное мёртвое поле на уровень ниже: `EffectiveProfileCandidate.independentEvidenceCount` (`types.ts:29`) — тоже никогда не устанавливается, и даже если бы устанавливалось, `build-effective-tobacco-profile.ts` его нигде не читает. Это не единичный недосмотр — это спроектированная, но так и не законченная ось confidence.

## Откуда эти данные должны реально браться

Важно развести два вопроса, которые по названию полей выглядят похоже, но концептуально разные.

### `proportionConfirmed` — «видели ли мы именно ЭТУ комбинацию и пропорцию раньше»

Это утверждение про КОНКРЕТНЫЙ РЕЦЕПТ (пара/набор товаров при конкретных процентах), а не про данные отдельного табака. Единственный источник, который может честно на это ответить — тот же самый, что уже использован в ADR-020 Step B: 37 `status=VERIFIED` миксов `Mixes_Internal`/`Mix_Components`.

**Но: этих данных сегодня нет ни в одном постоянном, запрашиваемом реестре.** ADR-020 извлекал только АГРЕГИРОВАННУЮ статистику по парам категорий через одноразовый скрипт — не сами рецепты (какие именно canonicalProductId, при каких процентах, в каком mixId). Чтобы подключить `proportionConfirmed`, нужен НОВЫЙ артефакт — `VerifiedMixRecipeRegistry` (~37 записей: mixId → список {canonicalProductId, процент}, reaction_class), сопоставимый по объёму работы с батчем Product Flavor Profile Registry, только для целых рецептов, а не отдельных измерений одного товара — плюс runtime-логика сравнения (с допуском по проценту).

Для подавляющего большинства возможных пользовательских комбинаций (любые 2–5 из 93 `REAL`-товаров при любом процентном соотношении — комбинаторное пространство на порядки больше 37) `proportionConfirmed` останется `false` — и это **честный, правильный ответ**, а не дефект. Проблема не в том, что поле почти всегда `false` — проблема в том, что оно `false` абсолютно всегда, даже для узкого набора комбинаций, которые действительно совпадают с историей.

### `independentEvidenceCount` — независимые источники ЧЕГО именно

Два кандидата на смысл, с разными последствиями:

**(а) Независимые источники самого РЕЦЕПТА** (несколько блогеров/каналов публиковали одну и ту же комбинацию). `Mixes_Internal` структурно хранит РОВНО один `source_author`/`source_channel`/`source_url` на строку микса — данных о повторных независимых публикациях того же рецепта в принципе нет. Это потребовало бы нового сбора данных, а не переподключения существующих.

**(b) Независимые источники ФЛЕЙВОР-ПРОФИЛЯ каждого табака** (переиспользовать evidence-массивы `PRODUCT_FLAVOR_PROFILE_REGISTRY` — у каждого измерения каждого из 86 продуктов уже есть 1–3 evidence-цитаты с типом/confidence). Эти данные УЖЕ СУЩЕСТВУЮТ, прямо сейчас, просто не используются живым scoring-пайплайном. **Но есть существенная оговорка**: это измеряло бы ровно то же самое, что ДОЛЖЕН измерять `profileReliabilityScore`/`profileCoverage` — просто через другую дверь. Переиспользование не является строго избыточным СЕГОДНЯ только потому, что `profileReliabilityScore` для всех 86 продуктов сейчас — плоская константа `60` (по `profileStatus=DRAFT`/`profileSource=MIXED`, единая для всех строк импорта), игнорирующая уже посчитанную в реестре реальную вариацию (`dataCompleteness` DETAILED/GOOD/BASIC/MINIMAL, `overallConfidence`). То есть тут на самом деле ДВЕ связанные, но разные проблемы: `profileReliabilityScore` сам по себе слишком грубый, И `independentEvidenceCount` не заполнен — вариант (b) частично чинил бы обе проблемы, пропуская ОДНИ И ТЕ ЖЕ данные реестра через два разных термина формулы, что является реальным дизайн-запахом (один сигнал, посчитанный дважды под разными именами), даже если формально это не «неверно».

## Стоит ли это того (10% веса, узкая область применения)

Посчитал ожидаемый эффект, если реализовать по максимуму (новый `VerifiedMixRecipeRegistry` для `proportionConfirmed` + переиспользование registry evidence для `independentEvidenceCount`):

- `confirmations`: `5` → до `8` (`+2` за `proportionConfirmed`, `+1` за `independentEvidenceCount≥2`) × вес `0.1` = **до +0.3 к финальному `predictedQualityScore`**, и только для миксов, точно воспроизводящих один из 37 известных рецептов.
- `predictionConfidence`: до `+14.5` из 100 (`+4.5` пропорция, `+10` evidence) — способно перевести конкретный микс через порог «Высокая», опять же только для совпадающих миксов.

**Охват — узкий.** При 93 `REAL`-товарах пространство возможных комбинаций из 2–5 компонентов на порядки больше 37 — увидеть `proportionConfirmed=true` сможет только пользователь, который случайно (или намеренно) воссоздаст один из 37 конкретных исторических рецептов. Подавляющее большинство пользовательских миксов по-прежнему будут показывать `confirmations=5`, как сегодня.

**Трудозатраты — не «починка проводки».** Это не подключение уже существующих данных, а создание нового реестра рецептов (реальная кураторская работа, по объёму сравнимая с мини-версией Product Flavor Profile Registry) плюс логика сопоставления с допуском по проценту, плюс решение по избыточности `independentEvidenceCount`.

### Моя рекомендация

Приоритет — **низкий-средний**, не срочно. Для сравнения: расширение категориальных правил (ADR-018/019/020) затрагивает КАЖДУЮ пару товаров, разделяющих категорию — широкий охват при умеренных трудозатратах. Здесь — узкий охват (только точное совпадение с 37 конкретными рецептами) при нетривиальных трудозатратах (новый реестр). Стоит сделать **когда-нибудь**, но не в приоритете относительно любой задачи, расширяющей категориальное покрытие (которое всё ещё далеко от завершения — например, review-список из 5 нерешённых конфликтов ADR-019 или расширение выборки verified-mix-history по мере роста истории).

Если всё же делать — рекомендую:
1. `proportionConfirmed`: строить `VerifiedMixRecipeRegistry`, сопоставлять на уровне **вызывающего кода** (`src/app/api/mixes/route.ts`), а не внутри `fromPrismaFlavor` — важное уточнение к формулировке задачи: `fromPrismaFlavor` вызывается для ОДНОГО компонента за раз (`input.components.map(component => fromPrismaFlavor(...))`) и не имеет доступа к остальным компонентам микса, а сопоставление с историческим рецептом по определению требует знать ВЕСЬ набор компонентов одновременно. Подключать нужно как отдельный шаг между сборкой `canonicalComponents` и вызовом `calculateMixAnalysis`.
2. `independentEvidenceCount`: не подставлять переиспользование evidence реестра как есть — сначала (отдельной задачей) почин `profileReliabilityScore`, чтобы он реально отражал `dataCompleteness`/`overallConfidence` каждого товара, а не плоскую константу `60` для всех 86; иначе получится задвоение одного сигнала под двумя разными названиями формулы confidence.

## Alternatives considered

- **Подключить `fromPrismaFlavor` буквально, как сформулировано в задаче.** Отклонено технически: функция не имеет контекста «весь микс», сопоставление с рецептом физически не может произойти на этом уровне.
- **`independentEvidenceCount` = число evidence-цитат из `PRODUCT_FLAVOR_PROFILE_REGISTRY` немедленно, без починки `profileReliabilityScore`.** Отклонено: создаёт задвоение одного и того же сигнала (реальность заполненности/качества данных товара) под двумя разными весами формулы, что менее честно, чем оставить `0` до полноценного решения.
- **Присвоить `independentEvidenceCount` фиксированную небольшую константу (например 1) для всех 86 новых товаров, раз у них у всех есть evidence хоть какого-то типа.** Отклонено: та же логика, что и запрет `STRONG_MATCH` из отсутствия negative в ADR-020 — константа не несёт дифференцирующего сигнала и создаёт иллюзию точности там, где её нет.
- **Не трогать вообще, оставить как есть.** Рассмотрено серьёзно: учитывая узкий охват и нетривиальные трудозатраты, это тоже разумный вариант — разница с рекомендацией «низкий приоритет» скорее в формулировке, чем по сути.

## Consequences (если будет реализовано в будущем)

- Появится новый артефакт `VerifiedMixRecipeRegistry` — требует отдельной кураторской работы (сопоставление identity, нормализация процентов) сопоставимой по объёму с мини-веткой Product Flavor Profile Registry.
- `confirmations` перестанет быть единственным полностью мёртвым компонентом `predictedQualityScore` — но эффект будет заметен только для миксов, воспроизводящих известную историю, не для произвольных пользовательских комбинаций.
- Потребуется отдельно решить судьбу `profileReliabilityScore` (сейчас плоская константа `60` для всех 86 продуктов) прежде, чем честно подключать `independentEvidenceCount` к registry evidence — иначе один и тот же факт будет влиять на score дважды под разными именами.
- Ничего не реализовано в этой сессии по явному указанию — анализ и рекомендация, ожидают решения.
