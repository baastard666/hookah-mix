# ADR-008: детерминированная идентификация товаров каталога

## Context

Технический registry v0.2.7 знает производителей и линейки, а текущий каталог хранит только `Brand.name` и `Flavor.name`. Для будущего связывания данных требуется понять, какие записи можно идентифицировать надёжно, не меняя каталог и не смешивая идентичность с техническим профилем.

## Decision

Создать отдельный чистый identity resolver, который читает только публичный API registry. Разрешать точные канонические имена, зарегистрированные aliases и известные boundary-aware префиксы в начале названия. Явные поля имеют приоритет; конфликт с разобранным префиксом сохраняется как warning. Неизвестные и неоднозначные значения возвращаются типизированными статусами и reason codes.

Запретить fuzzy matching, исправление опечаток и автоматическую транслитерацию. Формировать детерминированный Unicode-safe `productId` только для успешно разрешённых записей. Проводить аудит read-only и считать возможные дубли без автоматического изменения данных.

## Consequences

- ошибочные догадки не маскируются высоким confidence;
- пробелы каталога становятся измеримыми и объяснимыми;
- identity остаётся независимой от технических характеристик, анализа микса и UI;
- текущая Prisma-модель не требует миграции;
- `productId` пока вычисляется, а не хранится;
- расширение охвата требует проверенных aliases или явного поля линейки в источнике каталога.

## Alternatives considered

- fuzzy matching — отклонено из-за риска ложной идентичности;
- сохранение вычисленного результата в PostgreSQL — преждевременно и нарушает read-only цель итерации;
- размещение resolver внутри registry — смешивает две разные ответственности;
- автоматическое исправление каталога по результату аудита — исключено, так как аудит является диагностикой.
