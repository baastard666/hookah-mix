# ADR-022: перекалибровка весов `calculateMixConfidence` + методологическая прозрачность в UI

## Context

ADR-021 показал: `proportionCoverage` (15% веса формулы `calculateMixConfidence`) и `externalEvidenceCoverage` (10% веса) сегодня — зафиксированные на месте константы для **любого** микса в живой системе (`70` и `0` соответственно), потому что `fromPrismaFlavor` никогда не устанавливает `proportionConfirmed`/`independentEvidenceCount`. Следствие: лейбл «Высокая уверенность» структурно недостижим для любого прогноза в системе (не только для 86 новых продуктов) — максимум по теоретической прикидке ADR-021 составлял `71.5` при пороге `≥75`.

Пользователь принял рекомендацию ADR-021 не строить `VerifiedMixRecipeRegistry` сейчас (низкий приоритет, узкий охват), но справедливо указал: пока эти два поля не наполнены реальными данными, показывать пользователю недостижимый лейбл как часть постоянного интерфейса — вводит в заблуждение. Задача — минимальная правка презентации, не полная реализация ADR-021.

### Уточнение к ADR-021: `profileCoverage` — не плоская константа

При подготовке диагностики к этой ADR обнаружено, что предпосылка ADR-021 «`profileCoverage`=60 для всех 86 продуктов» была верна только как теоретический потолок для одного продукта, но не как реальное поведение `calculateMixConfidence`. Это разные метрики: `reliability()` (`from-prisma.ts`) — плоская `60` для каждой строки `Flavor` (по `profileStatus`/`profileSource`); а `profileCoverage` в `predictionConfidence` — среднее `reliabilityScore` по **всем 18 полям** `FlavorProfile` (`build-effective-tobacco-profile.ts:56`), где отсутствующие (`null`) поля подставляют низконадёжный `NEUTRAL_FALLBACK`-кандидат, а не сам `reliability()`. На реальных данных (см. диагностику ниже) `profileCoverage` варьируется от `21.3` до `60` в зависимости от того, сколько измерений заполнено у конкретных компонентов — то есть эта ось **уже несёт реальный сигнал о полноте данных**, в отличие от `proportionCoverage`/`externalEvidenceCoverage`.

Это не меняет вывод ADR-021 (`confirmations`/два новых поля остаются мёртвыми), но меняет обоснование выбора между вариантами ниже: перевешивать стоит именно на оси, которые differentiate по реальным данным, а `profileCoverage` — одна из них.

## Decision

Реализованы оба направления, предложенных пользователем как варианты (A — пересчёт весов, B — явное объяснение в UI), одновременно, как взаимодополняющие, а не альтернативные меры:

### A. Перекалибровка весов `calculateMixConfidence`

`src/lib/canonical-mix-scoring/calculate-mix-confidence.ts`: формула `score` изменена с

```
identityCoverage×0.4 + profileCoverage×0.35 + proportionCoverage×0.15 + externalEvidenceCoverage×0.1 − riskPenalty
```

на

```
identityCoverage×0.55 + profileCoverage×0.45 − riskPenalty
```

`proportionCoverage`/`externalEvidenceCoverage` **по-прежнему вычисляются и возвращаются** в `MixPredictionConfidence` (не убраны из типа/отчёта — сохранены для транспарентности и на случай будущей отладки), просто больше не участвуют в весе `score`. Обоснование — то же самое «null ≠ 0» правило, которое проект уже применил в ADR-015/017 к полям `FlavorProfile`: подмешивать в средневзвешенное значение константу, которая одинакова для 100% системы независимо от реального качества микса, эквивалентно занижению счёта на фиксированную величину, не несущую сигнала. В коде оставлен явный комментарий, что перераспределение — временная мера, привязанная к отсутствию `VerifiedMixRecipeRegistry` (ADR-021), а не постоянное архитектурное решение; веса нужно будет вернуть (или пересчитать заново), если/когда этот реестр появится и заполнит обе оси реальными значениями.

### B. Методологическая прозрачность в `confidenceReasons`

`src/lib/mix-result-presentation/index.ts`: в список причин (`confidenceReasons`), которые формируют `summary`/`reasons` карточки «Надёжность прогноза» (`src/app/result/[id]/page.tsx`), добавлен постоянный пункт: «Совпадение пропорций с проверенным рецептом и число независимых источников по этому сочетанию пока не отслеживаются и не влияют на оценку уверенности.» — не оправдание, а честное объяснение, откуда берётся оставшийся зазор до 100%. Лимит показываемых причин увеличен с 3 до 4 (`slice(0, 4)`), чтобы новый пункт не вытеснял уже существующие, более специфичные для конкретного микса причины.

**После:** диапазон `23.0–67.9`, лейблы по-прежнему только `{Предварительная, Средняя}` — **на этой конкретной выборке «Высокая» не достигнута ни разу**, и это ожидаемо и честно: `identity=100` даёт вклад `55`, и чтобы перейти порог `75`, нужен `profileCoverage≥44.4`, а в выборке он часто ниже (`21.3–42.5`) из-за реально пустых (`null`) вторичных/core-полей у конкретных компонентов — то есть новый потолок теперь определяется настоящей полнотой данных товара, а не искусственной константой. 3 пары перешли `Предварительная→Средняя` (учли выигрыш от `identity`), однако сама смена весов **не гарантирует** и не «подкручивает» лейблы вверх во всех случаях — пара `Element Мята + Sebero Лимон` (одна связка не найдена в каталоге, `identity=0`) даже слегка просела (`27.5→23.0`), потому что раньше её тянули вверх те самые зафиксированные `proportionCoverage=70`/`externalEvidenceCoverage=0` константы — это ровно ожидаемый эффект устранения занижения/завышения одинаковой для всех величиной.

## Alternatives considered

- **Просто понизить пороги 45/75.** Отклонено: это «инфляция оценок» — тот же самый недостижимый предел, только назван другим числом; не устраняет причину, что часть формулы не несёт сигнала.
- **Только вариант B (текст в UI, без изменения весов).** Рассмотрено как более консервативный минимум. Отклонено как недостаточное: объясняет проблему, но оставляет саму метрику структурно занижающей счёт на фиксированную величину для 100% миксов.
- **Полностью убрать `proportionCoverage`/`externalEvidenceCoverage` из типа/отчёта.** Отклонено: ломает публичный тип `MixPredictionConfidence` без необходимости и удаляет диагностическую видимость, которая понадобится, когда ADR-021 будет реализован.
- **Динамический вес (реактивируется автоматически, когда появятся ненулевые значения).** Рассмотрено, отклонено как избыточное усложнение для минимальной правки — пользователь просил минимальную меру; ручной откат при реализации ADR-021 достаточен и явно закомментирован в коде.

## Consequences

- `calculateMixConfidence` больше не занижает (и не завышает) счёт фиксированной величиной, не зависящей от конкретного микса; лейбл «Высокая» снова достижим в принципе (актуальный потолок теперь зависит от `identityCoverage`/`profileCoverage` конкретного микса — как и должно быть).
- Комментарий в коде явно фиксирует, что перераспределение весов нужно будет пересмотреть при реализации `VerifiedMixRecipeRegistry` (ADR-021) — иначе веса снова окажутся привязаны к устаревшей реальности данных.
- Пользователь теперь видит явное объяснение (`confidenceReasons`), что оценка пропорций/внешних источников пока не отслеживается — это не решает часть недостающего сигнала, но снимает вводящее в заблуждение впечатление, что низкая уверенность вызвана плохим миксом.
- Единственный тест, проверяющий конкретный лейбл (`canonical-mix-scoring.test.ts:201`, ветка `verifiedSmokeScore !== null` → `"Подтверждённая"`), не затронут — эта ветка вообще не доходит до сравнения с порогами `45/75`. Изменение прошло без правки тестов; полный прогон — зелёный.
