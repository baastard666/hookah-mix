# ADR-019: перенос внешнего исследования совместимости категорий в `CATEGORY_RELATIONS`/`NOTE_COMPATIBILITY_RULES`

## Context

ADR-018 перенёс `dominantNoteIds` реестра в Prisma `FlavorNoteAssignment`, но явно не решала вопрос содержания самих правил совместимости (`CATEGORY_RELATIONS`) — п.4 той ADR прямо выносил это в отдельную будущую задачу. Диагностика на паре `Sarma — 360 Крепкая Горная лаванда` (категория `FLORAL`) + `Daily Hookah — Сливки` (категория `DAIRY`→`CREAMY`) показала: обе категории теперь резолвятся верно, но пара всё равно оценивается нейтрально, потому что для `FLORAL+CREAMY` не было ни одной связи ни в одном направлении.

В этой сессии получен внешний батч из **29 пар категорий** с кодом совместимости (`STRONG`/`GOOD`/`CONDITIONAL`/`NEUTRAL`/`RISKY`) и уровнем доказательности (`HIGH`/`MEDIUM`/`LOW`), подготовленный сторонним исследованием — LLM-агрегированный веб-поиск по публичным источникам (официальные страницы производителей, HTReviews, форумы/сообщества, розничные описания), с реальными ссылками на источники, но **не** прямая ручная проверка силами проекта (в отличие от `evidence.editorial.taxonomy`/`evidence.internal.rules`, которые представляют собственную работу проекта).

**Автоматическая сверка всех 29 пар против существующих 24 записей `CATEGORY_RELATIONS`** (программно, а не на глаз — первый ручной проход пропустил один конфликт) дала:

| Категория проверки | Количество | Пары |
|---|---|---|
| Новые (нет пересечения) | 22 | см. Decision п.4 |
| Точное совпадение с существующей записью (тот же тип) | 2 | `FLORAL+BERRY` = `category.berry-floral` (`GOOD_MATCH`); `DAIRY+DESSERT`(→`CREAMY+DESSERT`) = `category.dessert-creamy` (`STRONG_MATCH`) |
| Конфликт с существующей записью (другой тип/знак) | 5 | см. таблицу ниже |

Конфликтующие пары:

| Пара | Существующая запись | Новые данные |
|---|---|---|
| `TEA+CITRUS` | `GOOD_MATCH` (0.4), `evidence.internal.rules` | `STRONG` / `HIGH` |
| `DAIRY+BERRY` (→`CREAMY+BERRY`) | `GOOD_MATCH` (0.4), `evidence.internal.rules` | `STRONG` / `HIGH` |
| `TEA+SPICE` (существует как `SPICE+TEA`) | `GOOD_MATCH` (0.4), безусловно | `CONDITIONAL` / `HIGH` |
| `MINT+DAIRY` (→`MINT+CREAMY`) | `RISKY` (-0.5) | `CONDITIONAL` / `MEDIUM` |
| `COFFEE+VANILLA` (существует как `VANILLA+COFFEE`) | `GOOD_MATCH` (0.4) | `RISKY` / `LOW` (единственный источник — розничное описание Deus Vanilla Berries) |

Особое требование пользователя: пары №26–29 исходного списка (`SPICE+BERRY`, `SPICE+VANILLA`, `COFFEE+BERRY`, `COFFEE+VANILLA`) **все происходят из одного источника** — розничного описания единственного товара Deus Vanilla Berries. Это маркетинговый текст про один конкретный продукт, а не независимое подтверждение сочетаемости категорий в целом, и должен получить наименьший вес/confidence из всей выборки.

## Decision

### 1. Новый evidence type — `AGGREGATED_RESEARCH`

Добавлено значение `AGGREGATED_RESEARCH` в `KnowledgeEvidenceType` (`src/lib/flavor-knowledge/types.ts`) и `EVIDENCE_TYPES` (`constants.ts`). Явно отделено от:
- `EDITORIAL_RESEARCH` — это собственная ручная таксономическая работа проекта;
- `INTERNAL_EXPERT_RULE` — эвристики без внешних ссылок, введённые при проектировании Knowledge Layer (ADR-002);
- `VERIFIED_TEST` — прямая ручная/лабораторная проверка;
- `COMMUNITY_AGGREGATE` — на сегодня единственная future-fixture запись, не связанная с этим батчем.

`AGGREGATED_RESEARCH` = «LLM-агрегированный веб-поиск с реальными ссылками на источники, не прямая ручная проверка».

### 2. Маппинг кода совместимости → `FlavorCategoryRelationType`

| Код | `FlavorCategoryRelationType` | `baseScore` |
|---|---|---|
| `STRONG` | `STRONG_MATCH` | `0.7` (как у существующих `STRONG_MATCH`) |
| `GOOD` | `GOOD_MATCH` | `0.4` |
| `CONDITIONAL` | `COMPLEMENTARY_CONTRAST` | `0.25` |
| `RISKY` | `RISKY` | `-0.4` |
| `NEUTRAL` | `NEUTRAL` | `0` |

`CONDITIONAL` (работает, но зависит от пропорций/условий) осознанно смаплен на `COMPLEMENTARY_CONTRAST`, а не на `GOOD_MATCH` с дополнительным флагом: в существующей таксономии `COMPLEMENTARY_CONTRAST` уже означает «положительный, но не безусловный» эффект (`DESSERT+SOUR`, `FRUIT+SPICE`, `TOBACCO+FRUIT`) — это точный семантический аналог, а не изобретение нового смысла.

`baseScore` **не** масштабируется по уровню доказательности — только по коду совместимости, тем же значением, что уже используют существующие 24 записи. Уровень доказательности выражается исключительно через вес evidence (см. п.3). Так проще и честнее: два независимых измерения («что нашли» и «насколько уверены») не сворачиваются в одно число.

### 3. Маппинг уровня доказательности → вес evidence

Добавлены 4 записи `KnowledgeEvidence` (`src/lib/flavor-knowledge/evidence.ts`), все типа `AGGREGATED_RESEARCH`:

| Уровень | `evidenceId` | `weight` | Обоснование |
|---|---|---|---|
| `HIGH` | `evidence.aggregated-research.high` | `0.7` | Несколько независимых типов источников (официальный сайт/рецепт + обзорный агрегатор + готовый вкус на рынке) |
| `MEDIUM` | `evidence.aggregated-research.medium` | `0.5` | Один тип источника или менее устойчивое сочетание |
| `LOW` | `evidence.aggregated-research.low` | `0.3` | Единичный пользовательский отзыв/сообщество |
| single-product-marketing | `evidence.aggregated-research.single-product-marketing` | `0.15` | **Ниже любого другого веса во всей таблице evidence** (прежний минимум — `evidence.inferred.taxonomy` = 0.3) |

Тест `66. ADR-019 п.2: single-product-marketing evidence has the lowest weight in the entire registry` механически проверяет, что `0.15` — минимум по ВСЕЙ таблице `FLAVOR_KNOWLEDGE_REGISTRY.evidence`, а не только среди новых 29 записей — более сильная гарантия, чем просто «ниже остальных 28».

Каждая новая запись `CATEGORY_RELATIONS` дополнительно несёт `metadata.sourceDescription` — конкретный тип источника из присланного списка (например «профильный блог + рецепты производителя»), для аудита без создания отдельной evidence-записи на каждую из 22 пар.

### 4. Конфликты с существующими записями — старые остаются, конфликтные пары не импортируются

Решение пользователя (после того как ему была явно показана таблица конфликтов): **существующие записи `CATEGORY_RELATIONS` не перезаписываются**. Ни одна из 5 конфликтующих пар (см. таблицу в Context) не добавлена и не изменена в этой сессии. Причина та же, что уже применялась к почти-дублям в ADR-016 и к содержательным конфликтам в целом: расхождение между эвристикой, заложенной при проектировании Knowledge Layer, и внешним агрегированным исследованием — content-решение, которое не должно приниматься автоматически односторонним «новое всегда лучше старого».

Тест `63` явно фиксирует значения всех 5 конфликтующих пар как regression-guard — если кто-то в будущем случайно «исправит» одну из них при рефакторинге, тест немедленно укажет, что это осознанное расхождение, а не забытая правка.

**Review-список конфликтов** (для будущего осознанного решения по каждой паре, по аналогии с near-duplicate review-списком ADR-016):

| Пара | Существующее (`internal.rules`/`editorial`) | Новое (`aggregated-research`) | Что нужно решить |
|---|---|---|---|
| `TEA+CITRUS` | `GOOD_MATCH` | `STRONG`/`HIGH` | Усилить ли до `STRONG_MATCH`? |
| `DAIRY+BERRY` | `GOOD_MATCH` | `STRONG`/`HIGH` | Усилить ли до `STRONG_MATCH`? |
| `TEA+SPICE` | `GOOD_MATCH`, безусловно | `CONDITIONAL`/`HIGH` | Понизить ли до условного? |
| `MINT+DAIRY` | `RISKY` | `CONDITIONAL`/`MEDIUM` | Развернуть с риска на условно-положительное? Требует наибольшей осторожности — прямой разворот знака. |
| `COFFEE+VANILLA` | `GOOD_MATCH` | `RISKY`/`LOW` (1 источник) | Скорее всего отклонить: единственный источник — маркетинговый текст про один товар, слабее уже существующей эвристики. |

Также 2 пары **подтверждают** уже существующие записи без изменений (`FLORAL+BERRY`, `DAIRY+DESSERT`) — новых записей для них не создано, дублирование `CATEGORY_RELATIONS` запрещено валидацией реестра (`validateKnowledgeRegistry` проверяет уникальность пар).

### 5. Подключение через `createKnowledgeCategoryRule` — 21 из 22

Все 22 новые записи добавлены в `CATEGORY_RELATIONS`. Но **подключено через `createKnowledgeCategoryRule` только 21** — `CITRUS+SPICE` (`NEUTRAL`, единственная нейтральная пара во всей выборке) не подключается: `createKnowledgeCategoryRule` намеренно бросает исключение для `NEUTRAL`-связей (см. `src/lib/mix-compatibility/knowledge-adapter.ts` — `NEUTRAL` не создаёт правило, это ноль эффекта по определению). `CITRUS+SPICE` тем не менее записана в `CATEGORY_RELATIONS` явно — это осознанная фиксация «проверили, оказалось нейтрально» (полярные отзывы), а не молчаливое отсутствие данных; тест `64` проверяет, что запись реально существует в реестре, а не просто возвращается по умолчанию.

Это прямо устраняет проблему, обозначенную ранее в этой же сессии («запись в `CATEGORY_RELATIONS` без `createKnowledgeCategoryRule` ничего не меняет в scoring») — теперь 21 из 22 реально влияют на `NOTE_COMPATIBILITY_RULES`/`analyzeNoteCompatibility`.

### 6. `FLORAL+DAIRY` — прямое закрытие пробела из диагностики Sarma+Сливки

`FLORAL+CREAMY` (пара №24 исходного списка, `CONDITIONAL`/`LOW`, единственный источник — единичный пользовательский отзыв) добавлена и подключена как `createKnowledgeCategoryRule("FLORAL","DAIRY")`. Это именно та связь, отсутствие которой было найдено при разборе пары `Sarma — 360 Крепкая Горная лаванда` + `Daily Hookah — Сливки` — результат диагностики после подключения показан в [PROGRESS-LOG.md](../PROGRESS-LOG.md).

Важная оговорка: доказательность этой конкретной пары — `LOW` (единичный отзыв), поэтому связь подключена с `baseScore=0.25` (`COMPLEMENTARY_CONTRAST`, наименьшая по модулю положительная категория из таксономии) — эффект на скор будет умеренным, соответствующим слабости источника, а не гарантированно крупным сдвигом.

## Consequences

- Диапазон `noteCompatibility`/`predictedQualityScore` должен продолжить расширяться для новых 86 продуктов реестра сверх эффекта уже полученного от ADR-018 — теперь дополнительно охвачены `MINT`, `TEA`, `CREAMY`(`DAIRY`), `FLORAL`, `ALCOHOL`, `SPICE`, `COFFEE`+`BERRY`/`VANILLA` в 21 новой комбинации.
- 5 пар из внешнего исследования сознательно НЕ импортированы и зафиксированы как review-список — это будущая content-задача, не техническая.
- Появился прецедент evidence-типа для будущих внешних исследовательских батчей (`AGGREGATED_RESEARCH`) — при следующем таком батче не нужно заново решать вопрос «как отличить агрегированное веб-исследование от собственной editorial-работы».
- Тест `63` фиксирует 5 конфликтующих значений как regression-guard — их изменение в будущем требует осознанной правки теста, а не может произойти случайно.
- `CITRUS+SPICE` — первая явно записанная `NEUTRAL`-связь в реестре (раньше `NEUTRAL` встречался только как значение по умолчанию для непроверенных пар); подтверждено тестом `64`, что это различие («проверено и нейтрально» vs «не проверено») теперь наблюдаемо в самих данных.

## Alternatives considered

- **Автоматически перезаписать все 5 конфликтующих записей новыми данными.** Отклонено пользователем явно: старая эвристика (`internal.rules`/`editorial`) и новое агрегированное исследование — источники разной природы, и молчаливая победа «более нового» источника не обоснована сама по себе (особенно для `COFFEE+VANILLA`, где новый источник — это ОДИН товар).
- **Смешать конфликтующие пары в общий импорт со средним/компромиссным значением.** Отклонено: усреднение `GOOD_MATCH` и `RISKY` не имеет содержательного смысла и маскирует реальное разногласие источников вместо того, чтобы сделать его видимым для будущего решения.
- **Масштабировать `baseScore` по уровню доказательности (например `RISKY` пар 26–28 сделать слабее -0.4).** Рассмотрено и отклонено в пользу более простой модели: код совместимости определяет `baseScore` по уже существующей шкале, confidence выражается только через evidence weight — два ортогональных измерения, не смешанные в одно число, проще для аудита и не требует изобретения новой шкалы дополнительно к уже существующей.
- **Создать отдельную evidence-запись на каждую из 22 пар (с конкретным текстом источника).** Отклонено: избыточно при 4 чётких confidence-уровнях; конкретный текст источника сохранён через `metadata.sourceDescription` на самой записи `CATEGORY_RELATIONS`, что не требует создания дополнительных 22 объектов `KnowledgeEvidence` ради индивидуального текста, не влияющего на расчёт.
- **Не подключать `CITRUS+SPICE` вообще, раз это NEUTRAL.** Отклонено: сам факт «проверили и это нейтрально» — не то же самое, что «не проверяли», и стоит отдельной, наблюдаемой записи для будущих исследователей, даже если она не участвует в scoring.
