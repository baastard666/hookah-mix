# ADR-014: целевая модель измерений Product Flavor Profile Registry

## Context

v0.3.5 создал независимый read-only Product Flavor Profile Registry (`src/lib/product-flavor-profile/`) с четырьмя измерениями (`sweetness`, `sourness`, `freshness`, `richness`) для `RESOLVED`-продуктов Tobacco Identity Decision Registry. Отдельная оценка гипотетического шага «создать записи `Flavor` в Postgres из этого registry» показала, что модель Prisma `Flavor` требует 18 обязательных числовых сенсорных полей (`strength`, `heatResistance`, `intensity`, `sweetness`, `acidity`, `cooling`, `creaminess`, `bitterness`, `dryness`, `juiciness`, `freshness`, `dessertLevel`, `spiceLevel`, `floralLevel`, `herbalLevel`, `smokyLevel`, `naturalness`, `persistence`).

Разбор по каждому из 18 полей показал резко разное качество доступных источников:

- 7 полей (`strength`, `heatResistance`, `intensity`, `sweetness`, `acidity`, `juiciness`, `freshness`) имеют тот же класс надёжных источников, что уже использовался для `sweetness`/`sourness`/`freshness` в batch 1–2: официальные страницы производителей, HTReviews, независимые обзоры ритейлеров;
- 9 полей (`cooling`, `creaminess`, `bitterness`, `dessertLevel`, `spiceLevel`, `floralLevel`, `herbalLevel`, `smokyLevel`, `dryness`) собираемы только для узкой категорийно-релевантной подгруппы товаров (например, `cooling` — только для ментоловых позиций); для остальных товаров источники молчат, и присвоение «0 по умолчанию» было бы угадыванием, а не фактом;
- 2 поля (`naturalness`, `persistence`) не являются вкусовыми измерениями по существу: `naturalness` — субъективное восприятие «натуральности» аромы конкретным дегустатором, а не вкусовая ось; `persistence` сильно confounded техникой курения (забивка, уголь, прогрев) конкретного обзорщика, а не только свойством табака.

Отдельно обнаружено, что уже существующее измерение `richness` было определено как «насыщенность/интенсивность вкуса» — то есть дублирует понятие, которое в Prisma называется `intensity`. Два имени для одного понятия создают путаницу при будущем сопоставлении registry с Prisma.

## Decision

1. Целевая модель измерений Product Flavor Profile Registry — **7 измерений**, не 18: `sweetness`, `sourness`, `freshness`, `intensity`, `strength`, `heatResistance`, `juiciness`. `sourness` и `freshness` сохраняют доменные имена registry (не переименовываются в `acidity`/`cooling` Prisma); сопоставление имён при будущей персистентности — отдельный вопрос вне этого ADR.
2. `richness` переименован в `intensity` как устранение дублирования понятия «насыщенность вкуса» — это переименование существующего ключа, а не пересчёт значения; данные и evidence самого измерения не менялись.
3. Остальные 11 полей Prisma (`cooling`, `creaminess`, `bitterness`, `dessertLevel`, `spiceLevel`, `floralLevel`, `herbalLevel`, `smokyLevel`, `dryness`, `naturalness`, `persistence`) **не входят** в `FlavorDimensionId` — ни как активно используемые измерения, ни как зарезервированные на будущее nullable-варианты типа. Отсутствие поля в типе — явная политика, а не временный пробел. Если для конкретного продукта в будущем найдётся сильный, проверяемый evidence по одному из этих 11 полей — это отдельное будущее решение (по аналогии с прецедентом данного ADR), а не текущая политика по умолчанию.
4. Batch 1–2 (30 уже заполненных продуктов) не пересчитываются задним числом под 3 новых измерения (`strength`, `heatResistance`, `juiciness`) в момент принятия этого ADR. Приоритет следующего исследовательского прохода — сначала добрать эти 3 измерения для уже покрытых 30 продуктов (у них уже подтверждена `RESOLVED` identity и есть частичные данные), и только затем расширять batch 3+ на новые продукты по той же очереди приоритизации (`verifiedMixCount → componentOccurrenceCount → occurrenceCount`, с manufacturer-tier tie-break из `priority-queue.ts`).
5. Prisma schema не меняется в рамках этого ADR. Вопрос фактической персистентности значений в Postgres (создание строк `Flavor`, сопоставление имён полей, политика для 11 исключённых полей при потенциальной будущей интеграции) остаётся отдельным будущим решением и не покрывается этим документом.

## Consequences

- Registry остаётся полностью evidence-backed: не появляется ни одного измерения, для заполнения которого потребовалось бы угадывать значение при молчании источников.
- Будущее сопоставление с Prisma `Flavor` становится частичным по построению: максимум 7 из 18 обязательных полей смогут получить обоснованное значение из этого registry уже сейчас; остальные 11 всегда потребуют либо отдельного источника данных, либо явного architectural решения (например, ослабление NOT NULL в отдельной будущей миграции), которое не принимается этим ADR.
- `FlavorDimensionId` — фиксированный список из 7 элементов; добавление любого нового измерения (в том числе любого из исключённых 11) требует нового ADR или явного изменения этого документа, а не тихого расширения типа.
- Batch 1–2 временно неполны по трём новым измерениям (`strength`, `heatResistance`, `juiciness` отсутствуют у всех 30 уже заполненных продуктов) — это ожидаемое переходное состояние, устраняемое следующим исследовательским проходом, а не дефект текущих данных.
- `overallConfidence`/`validateProductFlavorProfile` продолжают работать без изменений логики: правило «не выше минимального confidence среди заполненных измерений» применяется к любому подмножеству из 7 измерений одинаково.

## Alternatives considered

- Оставить 18 полей Prisma как целевую модель registry, заполняя пробелы нейтральными дефолтами при молчании источника — отклонено: прямое нарушение evidence/confidence принципа (ADR-003) и практики, уже установленной в batch 1–2 (`urban-soul-pineapple`, `husky-kiwano` и др. намеренно оставлены без выдуманных значений).
- Держать `richness` и `intensity` как два отдельных измерения — отклонено: подтверждено, что это один и тот же концепт «насыщенность/интенсивность вкуса»; раздельное существование только создавало бы путаницу при будущем сопоставлении с Prisma.
- Включить остальные 11 полей в `FlavorDimensionId` как формально допустимые, но пока не заполняемые (`Partial`-опция «на будущее») — отклонено явно: `Partial<Record<...>>` уже допускает отсутствие любого измерения технически, но присутствие поля в самом списке допустимых id снижает порог для будущего необоснованного заполнения нулём. Явное отсутствие в типе — более сильная гарантия, чем расчёт на дисциплину при заполнении.
- Пересчитать batch 1–2 сразу под новые измерения в рамках этой сессии — отклонено: требует нового раунда веб-исследования (вне рамок текущей задачи, ограниченной ADR и обновлением `types.ts`); отдельный последующий проход обязан начать именно с этих 30 продуктов, а не с новых.
